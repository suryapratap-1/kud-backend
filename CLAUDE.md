# Kudos API (kudos-api)

Full project context (decisions, history, status, next steps): @docs/CONTEXT.md

Express + TypeScript backend for Kudos, a testimonial platform. The Next.js frontend lives in a separate repo (`../wondering`) and talks to this API over HTTP. All data, auth, email, uploads and billing live here.

## Layout
- `src/index.ts` starts the server; `src/app.ts` wires middleware and routes in a deliberate order (see comments there).
- `src/env.ts` validates every setting at startup. Read config through `env`, never `process.env`.
- `src/routes/`: `public.ts` (review page, wall, review submission and confirmation, `/public/config`), `open.ts` (`/widgets/:id` and `/media/*`, any origin, no cookies), `dashboard.ts` (owner routes, login required), `billing.ts`, `webhooks.ts` (Razorpay, raw body).
- `src/lib/`: auth (Better Auth at `/auth`), billing (Razorpay REST), storage (R2/S3 or local `.storage/`), rate limiting, CAPTCHA, file signatures, plan rules.
- `src/db/`: Drizzle schema, seed. Migrations in `drizzle/`. Auth tables in `src/db/schema/auth.ts` are generated by `@better-auth/cli generate`; regenerate instead of hand-editing.

## Commands
- `docker compose up -d`: local Postgres on 127.0.0.1:5434 and Mailpit (inbox at http://localhost:8025)
- `pnpm dev` (port 4000), `pnpm build` (tsup → `dist/`), `pnpm start`, `pnpm typecheck`
- `pnpm db:generate` after schema changes, `pnpm db:migrate`, `pnpm db:seed` (local databases only; demo@kudos.local / kudos-demo-123)
- `pnpm billing:setup` creates the Razorpay plans once per account

## Security rules (do not break)
- Login uses Better Auth session cookies. In production the frontend and API share a parent domain (`COOKIE_DOMAIN`), e.g. app.kudos.com + api.kudos.com.
- CORS: cookie routes allow only `FRONTEND_URL`; `/widgets` and `/media` allow any origin without cookies. Mount each CORS policy on explicit paths so it can't apply to other routes.
- `requireTrustedOrigin` refuses state-changing requests whose Origin isn't the frontend (CSRF).
- Every route validates params and bodies with zod (`valid()` in `src/http.ts`) before touching the database, and every owner query is scoped to the session user's spaces. Another user must get 404, never someone else's data.
- Uploads: only the types in `src/lib/media-types.ts`, checked against file signatures; the server picks the stored name and Content-Type. Multer enforces size limits while streaming; the review route also rejects unsized or oversized bodies before reading.
- Review email links open the frontend's `/review-confirm`; only the form POST to `/public/reviews/verify` verifies (email scanners open links).
- Visitor IPs come from `clientIp()`: `CLIENT_IP_HEADER` or Express `req.ip` with `TRUST_PROXY` hops. Never read X-Forwarded-For directly.
- Plan access goes through `getPlan`/`getPlanForSpace`, never subscription status directly.
- Deleting a space also deletes its reviewers' files (`deleteFiles`).
- Response shapes are mirrored in the frontend (`apps/web/src/lib/api/types.ts`, and `WidgetPayload` in `apps/widget/src/render.ts` ↔ `src/lib/widget-types.ts`). Change both repos together.
